# classapp

Веб-приложение для учёта дел школьного класса и **полный DevOps-контур вокруг него**: инфраструктура как код,
Kubernetes, отказоустойчивая (по конфигурации) база данных, CI/CD с проверками безопасности, мониторинг,
бэкапы и восстановление. Проект выполнен как дипломная работа по администрированию серверов.

## 1. Что делает приложение

Flask-приложение (Python 3.11, SQLAlchemy, Alembic, gunicorn) для родительского комитета класса:

- **Пользователи и роли**: родитель, ученик, администратор. Вход по номеру телефона и паролю (пароли хранятся только
  хэшами). Администратор создаётся автоматически при первом запуске из секрета Kubernetes.
- **Задачи** с приоритетом, сроком и комментариями; **новости** с изображениями; **расписание** уроков и звонков;
  **общая информация** с вложениями.
- **Финансы**: взносы, расходы, отчёты о расходах, загрузка чеков (jpg/png/webp/pdf).
- **Состав класса** (ученики).
- **Аудит**: журнал входов и изменяющих действий, счётчик неудачных входов (используется в алертах).
- Служебные адреса: `GET /healthz` (проверка живости и доступности БД), `GET /metrics` (метрики Prometheus).

Схема БД меняется **только миграциями Alembic** (`alembic/versions/`), приложение само таблицы в продакшене не создаёт.
Это значит, что структуру базы данных (какие есть таблицы, колонки и связи) в продакшене меняет один инструмент, Alembic. Само приложение этого не делает.

Схема БД описывает, какие в базе таблицы (user, task, news, payment и т. д.) и какие в них колонки.

Миграция — это маленький файл-инструкция вроде «добавить колонку priority в таблицу task». Они лежат в alembic/versions/ и идут по порядк
Так сделано по нескольким причинам:

Контроль. Изменение схемы проходит осознанно: отдельный файл, проверка в CI, отдельный шаг деплоя.
Безопасность данных. create_all() не умеет менять уже существующие таблицы, а миграции умеют, и данные при этом сохраняются.
Версионирование. История изменений схемы лежит в git, как и код.
Нет гонок. Если бы две реплики web при старте одновременно меняли схему, они мешали бы друг другу. Миграции выполняет один Job.
В проекте это выглядит так:

CI (задание migrations) прогоняет миграции на пустой PostgreSQL. Затем alembic check убеждается, что модели в коде и миграции не расходятся, а потом проверяет откат и повторный накат.
Деплой (шаг 5 в deploy-steps.sh) запускает Job classapp-migrate с командой alembic upgrade head. Только после его успеха выкатываются новые web-поды.
Приложение при старте видит готовую схему. Если таблицы user ещё нет, оно просто пропускает создание администратора и пишет в лог, что ждёт миграций.

```

                            │  только порт 80 (и 443 в security group)
                            ▼
┌───────────────────────── AWS (eu-north-1) ─────────────────────────────────┐
│  Elastic IP ──► EC2 t3.small (Ubuntu 22.04, зашифрованный диск, IMDSv2)    │
│                 │                                                          │
│                 │  K3s (одноузловой Kubernetes)                            │
│                 │  ┌───────────────────────────────────────────────────┐   │
│                 │  │ nginx (hostPort 80)                               │   │
│                 │  │   /          ─► Service classapp-web-service      │   │
│                 │  │   /grafana/  ─► Grafana (если мониторинг включён) │   │
│                 │  │                                                   │   │
│                 │  │ classapp-web × 2..3 (HPA по CPU 70%)              │   │
│                 │  │     │                                             │   │
│                 │  │     ▼ Service classapp-db-master                  │   │
│                 │  │ Patroni + PostgreSQL 15 (StatefulSet, PVC 10 ГБ)  │   │
│                 │  │     ▲ выбор лидера                                │   │
│                 │  │ etcd (хранилище состояния Patroni)                │   │
│                 │  │                                                   │   │
│                 │  │ Job classapp-migrate (alembic upgrade head)       │   │
│                 │  └───────────────────────────────────────────────────┘   │
│                 │  systemd-таймер: ночной бэкап ──────────────┐            │
│                                                               ▼            │
│  EventBridge Scheduler: ВМ вкл 07:00 / выкл 22:00 (Минск)   S3-бакет       │
│                                                             бэкапов        │
│                                                             (хранение      │
│                                                             14 дней)       │
│                                                                            │
│  S3-бакет состояния Terraform (версии + шифрование)                        │
└────────────────────────────────────────────────────────────────────────────┘
  Оба бакета лежат в S3 того же аккаунта AWS, а не на ВМ, поэтому переживают
  удаление и пересоздание ВМ.
        ▲                                  ▲
        │ SSH (деплой, только по ключу)    │ образ по дайджесту
   GitHub Actions ───────────────────► GHCR (ghcr.io) — реестр образов
   (CI на любую ветку, деплой с main)
```

Ключевые принципы:

- **Единственная публичная точка входа** — nginx на порту 80. Prometheus, Grafana (NodePort), etcd, PostgreSQL снаружи недоступны.
- **Всё — код**: сеть, ВМ, бакеты, права, настройка ОС, K3s, секреты, манифесты, пайплайны. Ручных шагов в консоли нет.
- **Один и тот же образ** проходит тесты, сканирование, дымовой тест и затем уезжает в продакшен — пересборки нет.

## 4. Развёртывание с нуля одной командой

Требуется: `terraform`, `ansible`, `jq`, `git`, `ssh`, SSH-ключ (`~/.ssh/id_ed25519` или `id_rsa`) и доступ к AWS (`~/.aws`).

```bash
make up
```

`make up` — это три шага подряд, каждый можно запускать отдельно:

| Шаг | Команда | Что происходит |
|---|---|---|
| 1 | `make infra` | создаёт (идемпотентно) бакет состояния Terraform, затем применяет `terraform/aws`. Если план что-то **удаляет или пересоздаёт**, скрипт `safe-apply.sh` покажет это и спросит подтверждение |
| 2 | `make configure` | генерирует inventory из вывода Terraform, затем Ansible готовит ОС, ставит K3s, создаёт секреты, настраивает бэкапы |
| 3 | `make deploy` | копирует манифесты на ВМ и запускает `deploy-steps.sh`: БД → миграции → web/nginx → проверка |

Остальные команды: `make` без аргументов показывает справку и ничего не запускает; `make destroy` (удалить инфраструктуру с подтверждением), `make check` (те же проверки, что в CI),
`make start | stop | status` (управление ВМ), `make github-secrets` (записать в GitHub адрес ВМ и её SSH-отпечаток).

Пароли администратора приложения и Grafana генерируются Ansible **один раз** и сохраняются в `ansible/last-run.log`
(файл в `.gitignore`, права 600). Повторный прогон существующие секреты не перезаписывает.

Предварительное условие: образ `main-<sha>` должен лежать в GHCR, то есть CI на `main` должен был пройти хотя бы раз.

## 5. Инфраструктура: Terraform (AWS)

Каталог `terraform/aws/`. Регион `eu-north-1`, провайдер `hashicorp/aws ~> 5.0`.

| Ресурс | Файл | Зачем |
|---|---|---|
| `aws_instance.k3s` | `main.tf` | ВМ `t3.small` (2 vCPU / 2 ГБ), Ubuntu 22.04, диск gp3 30 ГБ **зашифрован**, IMDSv2 обязателен |
| `aws_eip.master1` | `main.tf` | статический IP: не меняется при остановке и запуске |
| `aws_security_group.k3s` | `main.tf` | входящие: 22 (SSH), 80 и 443; исходящие — любые |
| `aws_key_pair.classapp` | `main.tf` | публичный SSH-ключ оператора |
| `aws_s3_bucket.backups` + шифрование, блокировка публичного доступа, срок хранения | `main.tf` | хранилище бэкапов (14 дней) |
| `aws_iam_role.node` + инстанс-профиль | `main.tf` | ВМ пишет в бакет **через роль**, ключи на диск не кладутся; права только `PutObject`, `GetObject`, `ListBucket` на этот бакет |
| `aws_scheduler_schedule.start/stop` + роль | `schedule.tf` | EventBridge Scheduler включает ВМ в 07:00 и выключает в 22:00 по Минску: экономия кредитов (ночью платим только за диск и IP) |

**Состояние Terraform** лежит не в локальном файле, а в S3-бакете `classapp-tfstate-<account>`: версионирование, шифрование,
запрет публичного доступа. Бакет создаёт `terraform/bootstrap-state.sh` (он сам не управляется Terraform, чтобы не удалиться
вместе с инфраструктурой).

**`safe-apply.sh`** — защита от случайной потери данных: план сохраняется, анализируется, и если среди изменений есть
удаление/пересоздание ресурса (например, ВМ с данными), требуется ввести `yes`. Применяется именно сохранённый план.

Параметры (размер ВМ, расписание, разрешённые адреса для SSH, срок хранения бэкапов) — в `variables.tf`; пример значений —
`terraform.tfvars.example`.

## 6. Настройка сервера: Ansible

Каталог `ansible/`, точка входа — `playbook.yml`. Два «акта»:

1. **Все узлы** (`common`, `k3s`):
   - `common`: базовые пакеты, Python-клиент Kubernetes, **swap-файл 2 ГБ** (страховка от OOM на узле с 2 ГБ RAM).
   - `k3s`: установка K3s `v1.30.8+k3s1` (лёгкий Kubernetes, Traefik отключён — вход делает наш nginx). Роль умеет и
     дополнительные master-узлы, и worker-узлы (для режима демонстрации с несколькими узлами), токен кластера хранится
     в `ansible/group_vars/secrets.yml` (создаётся автоматически, права 600, в `.gitignore`, в образ не попадает).
2. **Первый master** (`bootstrap_secrets`, `monitoring`, `backup`):
   - `bootstrap_secrets`: создаёт Secret `classapp-secrets` (пароль БД, ключ сессий, учётка администратора) со
     случайными значениями **только если его ещё нет** — повторный запуск пароли не меняет.
   - `monitoring`: kube-prometheus-stack через Helm-контроллер K3s (включается флагом `MONITORING=true`, см. [§11](#11-мониторинг-и-логи)).
   - `backup`: скрипты `classapp-backup` и `classapp-restore` + systemd-таймер ночного бэкапа.

Все роли идемпотентны (повторный запуск ничего не ломает) и проверяются `ansible-lint` в CI.

## 7. Kubernetes: что и зачем запущено

Манифесты в `k8s/`, пространство имён `default`.

| Компонент | Тип | Реплик | Роль |
|---|---|---|---|
| `classapp-nginx` | Deployment | 1 | единая точка входа, занимает порт 80 хоста (`hostPort`), стратегия `Recreate` (иначе новый под не получил бы занятый порт) |
| `classapp-web` | Deployment + Service + HPA | 2 (авто 2–3 при CPU > 70%) | само приложение; пробы `/healthz` (readiness и liveness) |
| `classapp-patroni` | StatefulSet (Zalando Spilo 15) | 1 | PostgreSQL под управлением Patroni, данные на PVC 10 ГБ |
| `etcd` | Deployment | 1 | хранилище, в котором Patroni выбирает лидера |
| `classapp-migrate` | Job | 1 на деплой | `alembic upgrade head`; перед этим идемпотентно создаёт БД `classapp` |
| `classapp-db-master` / `classapp-db-replica` | Service | — | стабильные адреса: приложение всегда ходит в `classapp-db-master` |

Как приложение находит лидера БД: рядом с Patroni работает sidecar `role-labeler`, который каждые 10 секунд спрашивает
Patroni о роли пода и вешает на него метку `patroni-role=master|replica`. Service `classapp-db-master` выбирает под по
этой метке — при смене лидера трафик переключается сам.

**Усиление безопасности подов** (где это возможно): запуск не от root, `readOnlyRootFilesystem`, сброс всех Linux
capabilities, `allowPrivilegeEscalation: false`, профиль seccomp `RuntimeDefault`, лимиты CPU и памяти. Исключения (образы
Spilo и etcd пишут в корневую ФС) оформлены в `.trivyignore.yaml` с обоснованием.

**Сетевые политики** (`k8s/networkpolicy.yaml`): к etcd может подключаться только Patroni, к PostgreSQL — только web,
Job миграций и Patroni, к REST API Patroni — Patroni и Prometheus. Остальные поды кластера до БД не достучатся.
Если деплой упал, а политик до него не было, скрипт деплоя их удаляет, чтобы ошибка в политике не оставила БД недоступной.

Файл `k8s/kustomization.yaml` собирает весь стек для `kubectl apply -k k8s/`.

## 8. CI/CD: от коммита до продакшена

### 8.1 CI — на коммит в **любую** ветку (`.github/workflows/ci.yml`)

Параллельно запускаются проверки; если все зелёные — собирается и публикуется образ.

| Задание | Что проверяет |
|---|---|
| `lint` | black, isort, flake8, bandit (безопасность Python), shellcheck (shell), hadolint (Dockerfile), actionlint (workflow) |
| `secrets-scan` | gitleaks по всей истории: не закоммичены ли пароли и ключи |
| `dependency-audit` | `pip-audit`: известные уязвимости в зависимостях |
| `iac` | `terraform fmt/validate`, `ansible-lint`, `kubeconform` (валидность манифестов), Trivy config (небезопасные настройки IaC/Dockerfile/манифестов) |
| `test` | pytest на SQLite **и** PostgreSQL, покрытие кода не ниже 70%, отчёты сохраняются как артефакты |
| `migrations` | на пустой PostgreSQL: `upgrade head` → `alembic check` (модели и миграции не расходятся) → `downgrade base` → снова `upgrade head` |
| `build` | сборка образа **один раз** → скан Trivy (HIGH/CRITICAL блокируют) → **дымовой тест** (миграции + запуск контейнера с теми же ограничениями, что в Kubernetes: не root, read-only, без capabilities; проверка `/healthz`, входа администратора, закрытого API) → SBOM → публикация в GHCR → подписанные аттестации |
| `notify` | сообщение о результате в Telegram |

Образ публикуется с тегом `<ветка>-<sha>`; из `main` дополнительно `latest`. Артефакты (отчёты тестов 14 дней, SBOM 90 дней)
сохраняются в хранилище GitHub Actions, образы — в GHCR.

### 8.2 CD — только `main` (`.github/workflows/deploy.yml`)

Запускается автоматически после **успешного** CI на `main`, также вручную (*Actions → Deploy to Production → Run workflow*
с полным SHA коммита — например, если коммит пришёл, пока ВМ была выключена по расписанию).

1. Проверка входных данных (SHA — ровно 40 hex-символов).
2. Определение **дайджеста** образа `sha256:…` — неизменяемого идентификатора (тег можно перезаписать, дайджест нельзя).
3. **Проверка подписи происхождения** (`gh attestation verify`): образ собран именно нашим `ci.yml` из этого репозитория.
   Подделанный или чужой образ не выкатится.
4. SSH к ВМ с проверкой отпечатка сервера (`SSH_KNOWN_HOSTS`, без него деплой не стартует).
5. Пропуск, если этот коммит уже выкачен (защита от дублей).
6. Загрузка манифестов и запуск `deploy-steps.sh` на ВМ.
7. Проверка снаружи: `curl http://<IP>/healthz`.
8. Уведомление в Telegram (успех или ошибка).

**`deploy-steps.sh`** по шагам: снять taint с узла → применить etcd и Patroni → дождаться, пока у БД появится лидер →
нормализовать секрет `classapp-secrets` → **миграции** → применить web и nginx с образом по дайджесту → дождаться готовности
каждого компонента → **проверка** `/healthz` (БД ok) и страницы входа → записать выкаченный SHA → отметка деплоя на графиках
Grafana (необязательно) → очистка неиспользуемых образов.

**Автооткат:** на любой сбой скрипт возвращает на прежнюю ревизию **все** компоненты, которые этот деплой успел изменить
(etcd, Patroni, nginx, web). Проверка работоспособности после раскатки обязательна.

Защита деплоя: окружение `production` доступно только ветке `main`; одновременно идёт только один деплой
(`concurrency`); действия GitHub закреплены по SHA коммита; минимальные права токена; значения из событий не подставляются
в shell напрямую (защита от инъекции).

Секреты GitHub: `SSH_HOST`, `SSH_KNOWN_HOSTS` (оба записывает `make github-secrets`), `SSH_KEY` (приватный ключ, один раз
вручную), опционально `SSH_PORT`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. После **любого** пересоздания ВМ выполните
`make github-secrets` заново.

Запасной вариант на случай недоступности SSH: pull-деплой по таймеру на самой ВМ (`scripts/pull-deploy/install.sh`),
по умолчанию только установлен и **выключен**, чтобы два пути не гонялись за один коммит.

## 9. Безопасность

| Слой | Меры |
|---|---|
| Исходный код | bandit, gitleaks по истории, pre-commit (`detect-private-key`) |
| Зависимости | версии закреплены; `pip-audit` блокирует CI; Dependabot присылает **только** обновления безопасности |
| Образ | не root (uid 1000), нет `setuptools`/`wheel` в итоговом образе, Trivy, SBOM, подписанные аттестации |
| Цепочка поставки | деплой по дайджесту + проверка подписи; Actions закреплены по SHA |
| Инфраструктура | Trivy config, `terraform validate`, зашифрованные диск и бэкапы, S3 без публичного доступа, IMDSv2, IAM с минимумом прав, ВМ ходит в S3 по роли без ключей |
| Секреты | не хранятся в git: Secret создаётся Ansible со случайными значениями; пароли в `last-run.log` (вне git) |
| Сеть | наружу только 80/443 и 22; Prometheus — только через SSH-туннель; `NetworkPolicy` ограничивает доступ к БД и etcd; nginx скрывает версию (`server_tokens off`) и добавляет заголовки `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`; SSH-отпечаток ВМ запоминается при первом подключении и дальше проверяется (Ansible, деплой) |
| Приложение | хэши паролей, `HttpOnly`/`SameSite` cookie, CSRF-защита форм, аудит входов, алерт на подбор пароля |

Все осознанные исключения сканера перечислены с причинами в `.trivyignore.yaml`.

## 10. База данных, бэкапы, восстановление

PostgreSQL 15 работает под Patroni (Zalando Spilo) с etcd; данные на PVC. Миграции — только Alembic (Job перед обновлением web).
**Миграции автоматически не откатываются**, поэтому каждая должна быть обратно совместима со старой версией приложения.

**Бэкапы** (роль `backup`): systemd-таймер `classapp-backup.timer` каждый день в 18:30 UTC (21:30 по Минску — за полчаса
до ночной остановки ВМ) запускает `classapp-backup`:

1. `pg_dump` из мастера Patroni → gzip; защита от пустого дампа;
2. архив каталога загрузок (чеки, изображения) — `/var/lib/classapp/uploads`;
3. оба файла уходят в S3 (`db/…sql.gz`, `uploads/…tar.gz`), хранятся 14 дней.

**Восстановление** (`classapp-restore` на ВМ):

```bash
sudo systemctl start classapp-backup       # сделать бэкап прямо сейчас
sudo classapp-restore verify               # проверить свежий бэкап во временной БД (боевую БД не трогает)
sudo classapp-restore apply                # ВОССТАНОВИТЬ БД и загрузки из свежего бэкапа (данные заменяются!)
sudo classapp-restore apply <файл.sql.gz>  # из конкретного дампа (aws s3 ls s3://<бакет>/db/)
```

`verify` загружает дамп во временную базу и выводит число таблиц, администраторов и версию миграций — так регулярно
проверяется, что бэкап **действительно восстанавливается**, а не просто существует. `apply` на время останавливает web и
возвращает его обратно.

Это пройденный сценарий: ВМ уже пересоздавалась (смена шифрования диска), данные были восстановлены из бэкапа.

## 11. Мониторинг и логи

> **Важно: на работающем сервере мониторинг сейчас отключён вынужденно.** Prometheus и Grafana вместе с K3s, Patroni,
> etcd и двумя репликами web не помещаются в 2 ГБ памяти ВМ `t3.small`: узел уходит в swap, API-сервер K3s перестаёт
> отвечать, а вместе с ним страдает и сам сайт. Приоритет отдан работоспособности приложения. Весь код мониторинга
> (роль Ansible, ServiceMonitor'ы, дашборды, правила алертов) готов и проверен, но по умолчанию не устанавливается
> (`MONITORING=false`). Сейчас в кластере нет подов в пространстве имён `monitoring`, поэтому Grafana (`/grafana/`)
> отвечает 502, а Prometheus недоступен. Сайт и база при этом работают, их состояние видно по `GET /healthz`.
> Включить мониторинг можно на время демонстрации или на более крупной ВМ (см. ниже).

- **Метрики**: приложение отдаёт `/metrics` (запросы, коды, длительность, попытки входа, действия пользователей);
  gunicorn с несколькими воркерами агрегирует их через `PROMETHEUS_MULTIPROC_DIR`. Patroni тоже отдаёт метрики.
- **Prometheus + Grafana** в Kubernetes ставит роль `monitoring` (kube-prometheus-stack, облегчённый профиль:
  без Alertmanager и лишних правил). Есть дашборды (`provisioning/dashboards_json/`: overview, audit) и ServiceMonitor'ы.
  Деплои отмечаются вертикальными метками на графиках.
- **Включение**: `make configure MONITORING=true`. По умолчанию **выключено**: стек не помещается в 2 ГБ памяти рядом
  с Patroni и web (включается на время демонстрации или на более крупной ВМ). Grafana открывается на `/grafana/`,
  Prometheus — через `ssh -L 9090:127.0.0.1:30900 ubuntu@<IP>`.
- **Алерты** (`monitoring/alert.rules.yml`): экземпляр недоступен 2 минуты, доля 5xx > 5%, более 15 неудачных входов за
  5 минут (подбор пароля), p95 ответа > 1,5 с.
- **Логи**: приложение пишет структурный JSON (`/var/log/classapp/app.json.log`), nginx — JSON-лог доступа. Стек
  Loki + Promtail (`docker-compose.logging.yml`, `promtail-config.yml`) собирает их в Grafana.

## 14. Принятые решения и известные ограничения


| Ограничение | Почему так / что планируется |
|---|---|
| **Один узел, одна реплика БД и etcd** | бюджет: free plan AWS и ВМ на 2 ГБ. Patroni/etcd настроены как для HA, но реального переключения при падении узла нет. Для демонстрации: профиль с несколькими узлами (роль `k3s` это поддерживает) |
| ВМ ночью выключена | экономия кредитов; побочный эффект — ночные деплои нужно запускать вручную |
| Порт 22 открыт для `0.0.0.0/0` | деплой идёт с раннеров GitHub с динамическими адресами. Защита: только ключи, проверка отпечатка. План: деплой через AWS SSM без открытого SSH (риск описан в `.trivyignore.yaml`) |
| Нет TLS и домена | не требуется заданием; куки не помечены `Secure`, включается переменной `SESSION_COOKIE_SECURE` |
| Нет блокировки состояния Terraform | у IAM-пользователя нет DynamoDB; оператор один; есть версионирование бакета (откат состояния). Возможно `use_lockfile` на Terraform ≥ 1.10 |
| Миграции БД не откатываются автоматически | они обязаны быть обратно совместимыми |
| **Мониторинг отключён вынужденно** | Prometheus и Grafana не помещаются в 2 ГБ памяти рядом с остальными компонентами, узел уходит в swap. Код готов, включается флагом `make configure MONITORING=true` на время демонстрации или на ВМ побольше (`t3.medium` и выше). На сервере сейчас не установлен |
| Alertmanager отключён | алерты видны в Prometheus/Grafana, отправки уведомлений по ним нет (Telegram получает только итоги CI/CD) |
| etcd без аутентификации | доступен только внутри кластера |
| Плановых обновлений версий нет | версии закреплены ради воспроизводимости; Dependabot — только исправления уязвимостей |
| Yandex Cloud (`terraform/` в корне) | исторический вариант; не поддерживается. Прежний продакшен потерян при пожаре ЦОД провайдера — именно после этого введены бэкапы в S3 и миграция на AWS |

## 15. Словарь терминов

- **IaC (инфраструктура как код)** — инфраструктура описана файлами и создаётся командой, а не кликами в консоли.
- **Terraform** — создаёт ресурсы в облаке (ВМ, сеть, бакеты). **Ansible** — настраивает уже созданный сервер.
- **K3s / Kubernetes** — система, которая запускает контейнеры, перезапускает упавшие и раскатывает обновления.
- **Patroni** — управляет PostgreSQL, выбирает лидера и следит за репликами; **etcd** — хранилище, где Patroni хранит, кто лидер.
- **Alembic** — инструмент миграций схемы БД. **HPA** — автоматическое добавление реплик при росте нагрузки.
- **GHCR** — реестр контейнерных образов GitHub. **Дайджест образа** — хэш `sha256:…`, однозначно определяющий содержимое.
- **SBOM** — перечень компонентов внутри образа. **Аттестация** — подпись, подтверждающая, кто и из какого коммита собрал образ.
- **Trivy / gitleaks / pip-audit / bandit** — сканеры: уязвимости и небезопасные настройки / секреты в коде / уязвимые зависимости / ошибки безопасности в Python.
