# 5. Terraform (AWS), Ansible, бэкапы и расписание ВМ

**Разделение труда:** Terraform создаёт «железо» в облаке (ВМ, адрес, сеть, бакет, роли); Ansible настраивает уже
существующую ВМ (пакеты, K3s, секреты, бэкапы). Затем `deploy-steps.sh` ставит приложение.

---

## 5.1. Terraform: основная инфраструктура `terraform/aws/`

Команды: `terraform init` (скачать провайдера и подключить хранилище состояния), `terraform plan` (показать, что изменится),
`terraform apply` (применить), `terraform destroy` (удалить). **Состояние** (`state`) — файл, где Terraform помнит, какие
ресурсы он создал. Оно лежит в S3, а не на вашем компьютере.

### `main.tf` — построчно
| Строки | Что делает |
|---|---|
| 1–2 | блок `terraform`; нужна версия Terraform не ниже 1.6 |
| 4–7 | `backend "s3" {}` — состояние в S3. Параметры (бакет, ключ, регион) пустые здесь и передаются командой `make tf-init`, потому что в этом блоке нельзя использовать переменные |
| 9–14 | провайдер AWS версии 5.x |
| 17–25 | настройки провайдера: регион из переменной; `default_tags` помечает все ресурсы тегом `Project=classapp` (удобно искать и считать стоимость) |
| 27 | `aws_caller_identity` — узнаёт номер вашего AWS-аккаунта (используется в имени бакета) |
| 29–39 | берёт **готовые** сеть по умолчанию (default VPC) и её подсети: для одной ВМ отдельная сеть не нужна |
| 41–50 | `aws_ami` — находит свежий образ Ubuntu 22.04 от Canonical (владелец `099720109477`) |
| 52–55 | `aws_key_pair` — загружает ваш публичный SSH-ключ в AWS, чтобы заходить на ВМ |
| 57–91 | **security group** (файрвол). Входящие: SSH (порт 22) с адресов из `allowed_ssh_cidrs`; порты из `public_tcp_ports` (80 и 443) отовсюду. Исходящие: всё разрешено. **Снаружи доступны только 22, 80, 443**; остальное (6443 — API Kubernetes, 30080 и пр.) закрыто |
| 95–98 | S3-бакет бэкапов `classapp-backups-<номер аккаунта>` |
| 100–108 | явное **шифрование бакета** (SSE-S3, AES-256, ключи AWS) |
| 110–116 | запрет любого публичного доступа к бакету |
| 118–131 | правило жизненного цикла: объекты удаляются через `backup_retention_days` (14) дней. **Поэтому состояние Terraform в этом бакете хранить нельзя** — оно бы удалялось |
| 133–145 | IAM-роль для ВМ: «ВМ имеет право представиться этой ролью» |
| 147–166 | политика роли: можно писать/читать объекты бакета бэкапов и перечислять его. Больше ничего. **Ключи доступа на диск ВМ не кладутся** — ВМ получает права через роль |
| 168–171 | профиль инстанса: связывает роль с ВМ |
| 175–181 | **ВМ**: образ, тип (`t3.small`), ключ, подсеть, файрвол, профиль роли |
| 183–190 | корневой диск: размер из переменной (30 ГБ), тип `gp3`, **`encrypted = true`** (шифрование EBS). Смена этого флага на уже созданной ВМ **пересоздаёт** её: данные возвращаются из бэкапа (`classapp-restore`), а `make infra` перед этим просит подтверждение |
| 191–195 | `http_tokens = "required"` — обязательный IMDSv2 (защита от кражи ролевых ключей через SSRF); `hop_limit = 2` — метаданные доступны и из подов |
| 197–201 | `ignore_changes = [ami]` — выход нового образа Ubuntu **не** приводит к пересозданию ВМ вместе с данными |
| 203–205 | имя ВМ `classapp-master-1` |
| 208–216 | **Elastic IP**: постоянный публичный адрес. Привязывается к ВМ; при остановке/запуске и даже пересоздании ВМ остаётся тем же |

### `variables.tf` — входные параметры
| Переменная | По умолчанию | Смысл |
|---|---|---|
| `region` | `eu-north-1` | регион AWS (Стокгольм) |
| `name_prefix` | `classapp` | префикс имён всех ресурсов |
| `instance_type` | `t3.small` | размер ВМ: 2 vCPU, 2 ГБ RAM |
| `boot_disk_size_gb` | 30 | размер диска |
| `allowed_ssh_cidrs` | `["0.0.0.0/0"]` | кому разрешён SSH. **Слабое место:** открыт всем (нужен GitHub-раннерам). Лучше ограничить |
| `public_tcp_ports` | `[80, 443]` | открытые публичные порты |
| `backup_retention_days` | 14 | срок хранения бэкапов |
| `ssh_public_key` | — (обязательная) | ваш публичный ключ |
| `schedule_enabled`, `schedule_timezone`, `schedule_start/stop_hour/minute` | `true`, `Europe/Minsk`, 7:00 и 22:00 | расписание работы ВМ |

### `outputs.tf` — результаты
`k3s_nodes` (структура с id, зоной, ролью, публичным и приватным IP; формат нужен для `generate_inventory.sh`),
`master1_static_ip` (значение для секрета GitHub `SSH_HOST`), `backup_bucket` (имя бакета бэкапов).

### `schedule.tf` — расписание работы ВМ
| Ресурс | Что делает |
|---|---|
| `aws_iam_role.scheduler` + `aws_iam_role_policy.scheduler` | роль, которую принимает планировщик; разрешает **только** `ec2:StartInstances` и `ec2:StopInstances` для **этой** ВМ |
| `aws_scheduler_schedule.start` | каждый день в 07:00 по `Europe/Minsk` (`cron(0 7 * * ? *)`) вызывает запуск ВМ |
| `aws_scheduler_schedule.stop` | каждый день в 22:00 — остановка ВМ |

`count = var.schedule_enabled ? 1 : 0` — расписание можно отключить переменной. Минск — UTC+3 без перехода на летнее время;
часовой пояс задаётся прямо в расписании. В остановленном состоянии платится только диск и IP, данные сохраняются.

### `terraform.tfvars.example`
Образец локального файла `terraform.tfvars` (сам он в `.gitignore`): публичный ключ и разрешённые адреса SSH. Реальные значения в репозиторий не попадают.

### `terraform/bootstrap-state.sh` — хранилище состояния
Идемпотентно создаёт S3-бакет `classapp-tfstate-<аккаунт>` (если его нет), включает **версионирование** (история состояния),
шифрование и запрет публичного доступа, и печатает параметры `-backend-config=...` для `terraform init`. Бакет не управляется
самим Terraform (курица и яйцо: нужен до первого `init`) и не удаляется командой `destroy`. Блокировок нет (оператор один).

### `terraform/generate_inventory.sh` — связка с Ansible
Берёт `terraform output k3s_nodes` и бакет бэкапов, находит SSH-ключ (`id_ed25519` или `id_rsa`) и записывает
`ansible/inventory/hosts.ini` с группами `[k3s_master]`, `[k3s_worker]`, `[k3s_cluster]` и переменными подключения
(`ansible_user=ubuntu`, ключ, `classapp_backup_bucket`). Файл в `.gitignore` (содержит реальный IP).

### `terraform/safe-apply.sh` — защита от случайного удаления
Используется командой `make infra` вместо «слепого» `terraform apply -auto-approve`. Строит план в файл, показывает итог, и если среди
изменений есть удаление или **пересоздание** ресурса (например, ВМ с данными) — просит ввести `yes`. Применяет именно сохранённый план.

### Проверки безопасности IaC
В CI Terraform проверяется `fmt -check`, `validate` и сканером Trivy (`trivy config`, уровни HIGH и CRITICAL). Принятые риски собраны в
`.trivyignore.yaml` с обоснованием каждого: исходящий трафик ВМ открыт (нужны apt, ghcr.io, K3s), порты 80/443 публичные по дизайну, порт 22
открыт для раннеров GitHub (динамические адреса; вход только по ключу; план улучшения — деплой через AWS SSM без открытого SSH),
шифрование бэкапов SSE-S3 вместо платного собственного ключа KMS. Всё остальное устранено в коде (шифрование диска и бакета).

### Legacy: корень `terraform/` (Yandex Cloud)
`main.tf`, `variables.tf`, `outputs.tf`, `terraform.tfvars.example`, `terraform.tfvars.demo.example` — прежний вариант в
Yandex Cloud (сеть, подсети, security group, `preemptible`-ВМ). Сохранён как история/запасной вариант; в работе не участвует.
`terraform/aws/.terraform.lock.hcl` и `terraform/.terraform.lock.hcl` фиксируют точные версии провайдеров (воспроизводимость).
`infra/terraform/` — остаток самых первых экспериментов (старое локальное состояние), в проекте не используется.

## 5.2. Ansible: настройка ВМ (`ansible/`)

Ansible подключается к ВМ по SSH и выполняет «задачи» (tasks) из «ролей» (roles). Задачи описывают **желаемое состояние**
(«пакет установлен»), а не команды, поэтому повторный запуск безопасен.

> **Качество кода Ansible.** В CI роли проверяет `ansible-lint` в самом строгом профиле `production`: переменные ролей имеют префикс
> с именем роли (`bootstrap_secrets_*`, `monitoring_*`), у команд заданы `changed_when`, в shell-конвейерах включён `pipefail`,
> в метаданных ролей указана лицензия.

### `ansible.cfg` — настройки
`inventory = inventory/hosts.ini`; `roles_path = roles`; `host_key_checking = False` (не спрашивать отпечаток ключа);
`timeout = 30`; в `[ssh_connection]` — `pipelining` (быстрее), повторы и `ControlPersist` (одно SSH-соединение на весь прогон).

### `playbook.yml` — построчно
| Строки | Что делает |
|---|---|
| 2–5 | первый play: хосты `k3s_cluster`, `become: true` (выполнять от root), сбор фактов отложен |
| 6–7 | подключает `group_vars/vault.yml` (там `k3s_token`) |
| 8–16 | перед ролями ждёт доступности SSH (до 300 с — ВМ могла только что запуститься) и собирает факты |
| 17–19 | роли **`common`** (пакеты, swap) и **`k3s`** (установка Kubernetes) |
| 21–26 | второй play: только на первом мастере |
| 27–35 | то же ожидание SSH |
| 36–40 | роли `bootstrap_secrets` (секреты приложения и Grafana), `monitoring` (**только если** `monitoring_enabled`), `backup` (бэкапы) |

### `group_vars/all.yml` — переменные для всех хостов
| Строки | Что делает |
|---|---|
| 5 | путь к интерпретатору Python на ВМ |
| 6 | `k3s_version: v1.30.8+k3s1` — **зафиксированная** версия K3s |
| 10–11 | адрес API Kubernetes (IP мастера) и порт 6443 |
| 12–14 | имя пространства имён и релиза мониторинга; путь к kubeconfig |
| 15 | **`classapp_admin_phone: "375290000000"`** — телефон администратора, попадает в секрет `admin-phone` |
| 24 | зеркала реестров не нужны (пустой словарь) |
| 29 | `monitoring_enabled: false` — мониторинг по умолчанию выключен (не помещается в 2 ГБ) |
| 32 | `swap_size_gb: 2` — файл подкачки 2 ГБ (страховка от нехватки памяти) |

### `group_vars/vault.yml(.example)`
Содержит `k3s_token` — общий «пароль» для присоединения узлов к кластеру. Создаётся один раз (`make configure`)
и переиспользуется. В `.gitignore`; `vault.yml.example` — образец.

### `inventory/hosts.ini(.example)`, `requirements.yml`
Список хостов и групп (генерируется из Terraform). `requirements.yml` — нужные коллекции Ansible (`kubernetes.core` >= 3.0).

### Роль `common` (`roles/common/tasks/main.yml`)
Ставит базовые пакеты (`curl`, `git`, `jq`, `python3-pip` и др.), Python-библиотеку `kubernetes` (нужна модулям Ansible для работы
с кластером), создаёт **swap-файл** (`fallocate`, `mkswap`, запись в `/etc/fstab`, `swapon`). `kubectl` отдельно не ставится:
его создаёт установщик K3s.

### Роль `k3s` (`roles/k3s/tasks/main.yml`)
Создаёт каталог настроек; при необходимости пишет `registries.yaml`; на первом мастере запускает официальный установщик
K3s с **зафиксированной версией** и `--disable traefik` (свой nginx вместо встроенного ingress), `--write-kubeconfig-mode 644`;
для дополнительных мастеров и воркеров есть отдельные задачи (присоединение по `K3S_URL` и `K3S_TOKEN`); включает и запускает
службу, ждёт порт 6443. Установка повторяется до 3 раз (сеть бывает нестабильной). Флаг `creates:` делает шаг идемпотентным.

### Роль `bootstrap_secrets` (`roles/bootstrap_secrets/tasks/main.yml`)
Проверяет, есть ли секрет `classapp-secrets`. **Если нет** — генерирует случайные пароли (БД, `secret-key`, админ) и создаёт
секрет; **выводит пароль администратора один раз** (`debug`), поэтому вывод Ansible сохраняется в `ansible/last-run.log`. Если секрет
уже есть — ничего не трогает (иначе пароль БД в секрете разошёлся бы с реальным). Так же создаёт пространство имён `monitoring`
и секрет `classapp-grafana`.

### Роль `monitoring` (`roles/monitoring/`)
Работает только при `monitoring_enabled=true`. Ставит `kube-prometheus-stack` через встроенный в K3s Helm-контроллер (ресурсы
`HelmChart` и `HelmChartConfig` с `files/values.yaml`), ждёт CRD `ServiceMonitor`, копирует и применяет `files/classapp-monitoring.yaml`
(см. файл 6).

### Роль `backup` (`roles/backup/`)
| Файл / задача | Что делает |
|---|---|
| `tasks/main.yml` строки 2–6 | ставит AWS CLI (`pip`) — только если бакет задан в inventory |
| 8–22 | создаёт `/etc/classapp` и пишет `backup.env` (имя бакета и регион, права 600) |
| 24–36 | устанавливает скрипты `classapp-backup` и `classapp-restore` в `/usr/local/bin` |
| 38–67 | создаёт systemd-юниты: **service** (`Type=oneshot`, запуск скрипта, таймаут 30 мин) и **timer** (`OnCalendar=*-*-* 18:30:00` = 21:30 по Минску, **за 30 минут до остановки ВМ**; `Persistent=true` — если ВМ была выключена в это время, бэкап выполнится после включения) |
| 69–75 | включает и запускает таймер |

**`files/classapp-backup.sh`** — построчно:
| Строки | Что делает |
|---|---|
| 4 | остановка при ошибке |
| 6–8 | читает настройки бакета; путь к kubeconfig; каталог загрузок `/var/lib/classapp/uploads` |
| 9–11 | метка времени UTC; временный каталог, удаляется при выходе (`trap`) |
| 13–14 | находит под Patroni с меткой `patroni-role=master`; нет — ошибка |
| 16–18 | выполняет в этом поде `pg_dump` базы `classapp` и сжимает `gzip` |
| 19–20 | **защита от пустого дампа**: если распакованный размер < 1000 байт — ошибка (иначе в S3 уехал бы «пустой» бэкап) |
| 22 | загружает дамп в `s3://<бакет>/db/classapp-<время>.sql.gz` |
| 24–27 | если каталог загрузок есть — архивирует его **целиком (включая `receipts/`)** и загружает в `uploads/` |
| 29 | сообщение об успехе |

**`files/classapp-restore.sh`** — `sudo classapp-restore verify|apply [файл]`:
`verify` создаёт временную базу `classapp_restore_test` **от `template0`**, загружает в неё дамп, печатает число таблиц, админов
и версию миграций и удаляет базу (боевую не трогает). `apply` останавливает web, пересоздаёт базу `classapp` из дампа,
распаковывает архив загрузок с тем же временем и возвращает web. Базу нужно создавать от `template0`: в `template1` у Spilo
уже есть служебные схемы, которые есть и в дампе.

### Что делает `make configure` целиком
`generate_inventory.sh` -> `vault.yml` (если нет) -> `ansible-galaxy collection install` -> `ansible-playbook` (вывод дописывается
в `ansible/last-run.log`).
