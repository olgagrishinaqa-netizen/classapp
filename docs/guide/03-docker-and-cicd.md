# 3. Docker, линтеры, CI/CD, Makefile и скрипты деплоя

## 3.1. Docker-образ

**Зачем Docker.** Образ — «коробка» с приложением и всеми зависимостями: одинаково работает на ноутбуке, в CI и на сервере.

### `Dockerfile` — построчно
| Строки | Что делает и зачем |
|---|---|
| 1 | `FROM python:3.11-slim-bookworm` — база: Python 3.11 в урезанном Debian 12 (меньше размер и поверхность атаки); версия ОС указана явно, обновления предлагает Dependabot |
| 3–4 | `ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1` — не создавать `.pyc`; выводить логи сразу, без буфера (иначе `kubectl logs` отстаёт) |
| 6 | создаёт непривилегированного пользователя `appuser` с **явным uid 1000** (на него ссылаются манифесты Kubernetes): приложение не работает от root |
| 7 | `WORKDIR /app` — рабочий каталог |
| 9–10 | отдаёт `/app` пользователю `appuser` |
| 11–12 | создаёт каталоги для логов (`/var/log/classapp`) и метрик нескольких воркеров (`/tmp/prometheus_multiproc`), отдаёт их `appuser` |
| 14–15 | **сначала** копирует только `requirements.txt` и ставит зависимости. Этот слой кэшируется: пока зависимости не менялись, пересборка быстрая (`--no-cache-dir` — не хранить кэш pip в образе) |
| 17–18 | копирует весь код с правами `appuser` |
| 20–22 | копирует `entrypoint.sh` и делает его исполняемым |
| 24 | `USER 1000:1000` — всё дальше (и запуск) идёт не от root; числовой uid нужен Kubernetes для проверки `runAsNonRoot` |
| 26–27 | `FLASK_CONFIG=config.ProdConfig` — образ по умолчанию боевой; `PROMETHEUS_MULTIPROC_DIR` — каталог метрик |
| 28 | `EXPOSE 8000` — документирует порт приложения |
| 29–30 | `HEALTHCHECK` — проверка `/healthz` для запуска вне Kubernetes (в K8s работают собственные пробы) |
| 29 | `ENTRYPOINT ["/entrypoint.sh"]` — всегда сначала запускается скрипт проверки/ожидания БД |
| 30 | `CMD [gunicorn -w 4 -b 0.0.0.0:8000 "app:create_app()"]` — команда по умолчанию (в Kubernetes переопределяется: 1 воркер) |

### `entrypoint.sh` — построчно
| Строки | Что делает |
|---|---|
| 2 | `set -euo pipefail` — остановка при любой ошибке, при использовании пустой переменной и в конвейерах |
| 5–6 | `: "${SECRET_KEY:?...}"` — если переменная не задана, скрипт падает с понятным сообщением (fail fast) |
| 9–24 | если `DATABASE_URL` не задан, собирает его из `POSTGRES_HOST/DB/USER` и `DB_PASSWORD`; пароль кодируется `urllib.parse.quote`, чтобы спецсимволы не ломали URL |
| 26–57 | встроенный Python-скрипт ждёт готовности БД: до `DB_WAIT_ATTEMPTS` (30) попыток через `DB_WAIT_INTERVAL` (2 с) пытается подключиться через `psycopg2`; нет — выход с кодом 3. Приложение и БД стартуют одновременно, без ожидания первый запрос упал бы |
| 59–60 | `exec "$@"` — запускает основную команду (gunicorn) **заменяя** процесс скрипта: gunicorn получает сигналы остановки (graceful shutdown) |

### `gunicorn.conf.py` — метрики при нескольких воркерах
Каждый воркер gunicorn — отдельный процесс; без доработки счётчики Prometheus «прыгали» бы. `on_starting` очищает
каталог метрик при старте, `child_exit` убирает данные завершившегося воркера. Обе функции ничего не делают, если
`PROMETHEUS_MULTIPROC_DIR` не задан.

### `.dockerignore`
Список того, что **не** попадает в образ при `COPY . .`: `.git`, `.env`, состояние Terraform (`*.tfstate`, `*.tfvars`), `ansible/last-run.log`
(пароли), тесты, документация, инфраструктурный код. Без него образ получал бы всё, что лежит рядом в рабочей папке, в том числе секреты.

### `requirements*.txt` — три слоя зависимостей
| Файл | Что в нём | Где используется |
|---|---|---|
| `requirements.txt` | только то, что нужно приложению в продакшене (Flask, SQLAlchemy, Alembic, gunicorn, psycopg2 и т. д.) с **точными версиями** | Docker-образ, job `migrations` и `dependency-audit` |
| `requirements-test.txt` | `-r requirements.txt` + pytest, pytest-cov, pytest-dotenv | job `test` |
| `requirements-dev.txt` | `-r requirements-test.txt` + pre-commit, pip-audit, ansible-lint, locust | рабочее место разработчика |

Раньше в образ попадали pytest, pre-commit, virtualenv и другие инструменты (лишняя поверхность атаки и уязвимости). Версии Flask 3.1.3 и
Werkzeug 3.1.9 подняты из-за найденных `pip-audit` уязвимостей.

### Compose-файлы (локальные стеки)
| Файл | Назначение |
|---|---|
| `docker-compose.dev.yml` | локальная разработка: PostgreSQL 15 (порт 5433) + контейнер Python, который ставит зависимости и запускает `flask run --debug` на 8080. Код монтируется с диска |
| `docker-compose.logging.yml` | локальный стек логов: Loki (хранилище), Promtail (читает файлы логов), Grafana с готовыми дашбордами из `provisioning/` |
| `docker-compose.prod.yml` | **устаревший** docker-стек (db + web + nginx + prometheus). В деплое не используется: прод работает на K3s |
| `nginx.conf` | конфиг nginx для этого устаревшего стека (upstream `web:8000`); в Kubernetes конфиг лежит в ConfigMap в `k8s/classapp-nginx.yaml` |
| `.env.sample` | образец переменных окружения |

## 3.2. Качество кода: линтеры

**Зачем.** Единый стиль и поиск типичных ошибок до попадания кода в репозиторий. Запускаются через **pre-commit** и в CI.

### `.pre-commit-config.yaml` — построчно
| Строки | Что делает |
|---|---|
| 1–6 | исключает из проверки `.venv`, `migrations`, `alembic` |
| 9–15 | базовые проверки: пробелы в конце строк, перевод строки в конце файла, слишком большие файлы, маркеры конфликта слияния; корректность YAML и TOML; **поиск приватных ключей** (`detect-private-key`) |
| 17–20 | **black** — автоформатирование кода |
| 22–25 | **isort** — сортировка импортов |
| 27–30 | **flake8** — поиск ошибок и нарушений стиля |
| 32–37 | **bandit** — поиск уязвимостей в `app/` (например, хардкод паролей, небезопасные вызовы) |
| далее | **shellcheck** (ошибки в shell-скриптах), **hadolint** (Dockerfile), **actionlint** (workflow GitHub Actions, включая инъекции через `${{ }}`) |

### `.flake8`, `pyproject.toml`
`.flake8`: максимальная длина строки 120, игнорировать `E203` (конфликт с black), не проверять `.git`, `__pycache__`, `.venv`, `alembic`.
`pyproject.toml`: настройки black и isort (длина строки 100, профиль `black`). Секция `[tool.flake8]` там
flake8 игнорирует (он читает `.flake8`), она оставлена как заметка.

### Прочее
`.gitignore` — что не попадает в git: окружение `.venv`, секреты `.env`, состояние и планы Terraform, `terraform.tfvars`,
сгенерированный inventory, `vault.yml`, **`ansible/last-run.log` (там пароли)**, загрузки, локальные БД.
`.gitattributes` — принудительные окончания строк LF (важно для shell-скриптов, чтобы они запускались на Linux).

## 3.3. CI/CD — GitHub Actions (`.github/`)

Два workflow. Образ собирается **один раз** в CI; деплой берёт именно этот образ.

```
push в любую ветку --> CI (ci.yml) --(успех, только main)--> Deploy to Production (deploy.yml)
```

### `ci.yml` — граф задач
```
lint ─────────┐
secrets-scan ─┤
dependency-audit ─┤
iac ──────────┼──> build (сборка, Trivy, дымовой тест, публикация) ──> notify
test (SQLite, PostgreSQL) ┤
migrations ───┘
```
Все проверки выполняются параллельно; сборка начинается только когда прошли **все**.

| Блок | Что делает | Зачем (практика) |
|---|---|---|
| `on: push` (без фильтра веток), `pull_request` в `main`, `workflow_dispatch` | запуск на любую ветку и вручную | требование диплома; для веток этого же репозитория с открытым PR `if:` пропускает дубль |
| `permissions: contents: read` | минимальные права токена на весь workflow | принцип наименьших привилегий; `packages: write` выдан только job `build` |
| `concurrency` | новый коммит отменяет старый прогон ветки, **кроме `main`** | в `main` каждый коммит должен получить образ и деплой |
| `runs-on: ubuntu-24.04`, `timeout-minutes` на каждом job | фиксированная ОС и ограничение времени | воспроизводимость; зависший job не висит 6 часов |
| `uses: ...@<sha> # vX` | все actions закреплены по SHA коммита | защита от подмены тега (атака на цепочку поставок); обновляет Dependabot |
| **`lint`** | `pre-commit` с хуками из раздела 3.2 (в том числе shellcheck, hadolint, actionlint) | единый стиль и статический анализ; блокирующий |
| **`secrets-scan`** | gitleaks по **всей истории** git (`fetch-depth: 0`) | секрет, однажды попавший в историю, остаётся там навсегда |
| **`dependency-audit`** | `pip-audit -r requirements.txt` | известные уязвимости зависимостей (нашёл Flask/Werkzeug/virtualenv) |
| **`iac`** | `terraform fmt -check` и `validate`; `ansible-lint` (профиль production); `kubeconform` (схемы Kubernetes 1.30, контрольная сумма скачанного бинарника проверяется); Trivy `config` (HIGH/CRITICAL) | «инфраструктура как код» проверяется так же строго, как приложение |
| **`test`** (матрица `sqlite`, `postgres`) | pytest на обеих СУБД; сервис-контейнер PostgreSQL 15; `--cov-fail-under=70`; отчёты `junit` и `coverage` в артефакты (14 дней, `if: always()`) | тесты на той же СУБД, что в проде; покрытие — реальный порог, а не декорация |
| **`migrations`** | на пустом PostgreSQL: `alembic upgrade head`, `alembic check` (модели и миграции не расходятся), `downgrade base`, снова `upgrade head` | сломанная миграция обнаруживается в CI, а не на боевой ВМ |
| **`build`** | см. ниже | |
| **`notify`** | Telegram по результатам всех задач; значения ветки, коммита, автора передаются через `env`, а не подставляются в команду | защита от инъекции через имя ветки |

**Задача `build` по шагам:**
1. Сборка образа через Buildx (`load: true`, кэш слоёв GitHub) — **единственная сборка**.
2. **Trivy image**: блокирует при уязвимостях HIGH/CRITICAL, для которых уже есть исправление (`ignore-unfixed`).
3. **Дымовой тест**: поднимает PostgreSQL, применяет миграции **внутри собранного образа**, запускает приложение с ограничениями как в Kubernetes
   (`--user 1000`, `--read-only`, `--cap-drop ALL`, `no-new-privileges`, tmpfs для `/tmp` и логов) и проверяет: `/healthz` с `database: ok`,
   страница входа 200, вход админа 200, закрытый API без входа 401. Так проверяется и то, что приложение работает при read-only файловой системе.
4. Только для `push`: вход в GHCR и **публикация того же образа** с тегом `<ветка>-<sha>` (для `main` ещё `latest`). Имя ветки приводится к допустимому виду.

### `deploy.yml` — построчно по шагам
| Блок | Что делает |
|---|---|
| `on: workflow_run` ("CI") и `workflow_dispatch` (вход `sha`) | запуск после CI либо вручную с указанием коммита |
| `concurrency: deploy-production`, `cancel-in-progress: false` | два деплоя одновременно невозможны, начатый не прерывается |
| `if:` | автоматически только для успешного CI, ветки `main`, события `push`; вручную всегда |
| `environment: production` | деплой привязан к окружению GitHub (можно включить обязательное одобрение и ограничить секреты) |
| `Validate inputs` | SHA обязан быть 40 hex-символов (защита от инъекции в команду на сервере), `SSH_HOST` задан |
| `Prepare SSH` | ключ берётся из секрета через `env` (не подстановкой в скрипт); **отпечаток сервера проверяется** (`StrictHostKeyChecking yes`, `known_hosts` из секрета `SSH_KNOWN_HOSTS`; если секрета нет — предупреждение и отпечаток берётся при первом подключении) |
| `Wait for SSH` | до 8 попыток по 15 с; понятная ошибка, если ВМ выключена по расписанию |
| `Upload manifests` | `tar`-архив `k8s/` и скриптов по SSH на ВМ (повторы) |
| `Deploy to K3s` | запуск `deploy-steps.sh <sha>` на ВМ (повторы) |
| `Verify from outside` | запрос к публичному `http://<IP>/healthz` с раннера: проверяет реальную точку входа (порт 80, nginx), а не только внутренности кластера |
| `Notify` | Telegram о результате деплоя |

**Секреты репозитория:** `SSH_HOST`, `SSH_KNOWN_HOSTS` (оба записывает `make github-secrets`), `SSH_KEY` (обязательные); `SSH_PORT`,
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (необязательные). `GITHUB_TOKEN` выдаётся GitHub автоматически.

**Если коммит пришёл ночью** (ВМ выключена по расписанию): деплой упадёт на ожидании SSH. Запустите ВМ (`make start`) и нажмите
*Re-run* либо *Run workflow* с SHA коммита.

### `dependabot.yml`
Раз в неделю предлагает pull request'ы с обновлениями: версий actions, Python-зависимостей, базового образа Docker и провайдера Terraform.

### `.trivyignore.yaml`
Принятые исключения сканера Trivy, **каждое с обоснованием**: открытые порты 80/443/22 (по дизайну), исходящий трафик, SSE-S3 вместо KMS,
`hostPort` nginx (единственный публичный порт), образы Patroni/etcd, которым нужны root или запись в корневую ФС. Всё остальное
уровня HIGH/CRITICAL блокирует CI.

## 3.4. Скрипты деплоя (`scripts/`)

### `scripts/pull-deploy/deploy-steps.sh` — шаги выкатки (общая логика)
Запускается на ВМ от root: `deploy-steps.sh <sha>`. Каждый шаг идемпотентен.

| Строки | Шаг | Что делает |
|---|---|---|
| 1–14 | заголовок | `set -euo pipefail`; параметры: коммит, репозиторий образа, каталог исходников, `KUBECONFIG`, имя образа `ghcr.io/<owner>/classapp:main-<sha>`; создаёт каталоги логов |
| 16–18 | ШАГ 1 | снимает taint (ограничение «не планировать поды») с мастер-ноды: на одной ноде все поды должны работать на ней |
| 20–34 | ШАГ 2 | применяет etcd, services и Patroni. Если StatefulSet нельзя изменить «на месте» (Kubernetes запрещает менять часть полей), пересоздаёт его с `--cascade=orphan`, не удаляя поды и данные |
| 36–50 | ШАГ 3 | ждёт до 15 минут, пока у сервиса `classapp-db-master` появится адрес (то есть Patroni выбрал лидера); при таймауте печатает диагностику |
| 52–69 | ШАГ 4 | читает из секрета `db-password`, `secret-key`, `admin-phone`, `admin-password`; собирает `database-url` (пароль URL-кодируется, `sslmode=require`); пересоздаёт секрет `classapp-secrets` через `--dry-run | apply` |
| 71–79 | ШАГ 5 | удаляет старый Job миграций, создаёт новый с образом нужного коммита (подмена тега через `sed`) и ждёт завершения до 10 минут; при ошибке показывает логи и **останавливает деплой** |
| 81–84 | ШАГ 6 | подставляет тег в `kustomization.yaml`, применяет `kubectl apply -k k8s/` (web, nginx, HPA), затем `set image` |
| 86–97 | ШАГ 7 | ждёт готовности Deployment до 5 минут; при неудаче делает **откат** (`rollout undo`) и завершает с ошибкой; затем до 15 раз проверяет `/healthz` через nginx на порту 30080 |
| 99–121 | ШАГ 8 | необязательно: ставит в Grafana аннотацию «Деплой <sha>» (вертикальная метка на графиках); если мониторинга нет — тихо пропускается |
| 123–132 | ШАГ 9 | очистка: журнал systemd старше 7 дней, неиспользуемые образы (`crictl rmi --prune`) |

### `scripts/pull-deploy/pull-deploy.sh` и `install.sh` — **запасной** pull-вариант
Вместо push по SSH можно, чтобы сама ВМ раз в 2 минуты опрашивала GitHub. `pull-deploy.sh`: берёт блокировку (`flock`,
чтобы не запускаться дважды), узнаёт последний коммит `main` (`git ls-remote`), проверяет, что образ `main-<sha>` уже есть в GHCR
(то есть CI и сборка прошли), затем запускает `deploy-steps.sh`. Неудачный коммит повторяется до 3 раз. Результат — в Telegram.
`install.sh` ставит скрипт и systemd-юниты (service + timer). По умолчанию таймер **не включается** (чтобы не конкурировать с `deploy.yml`);
включить: `sudo bash install.sh --enable`.

### `scripts/diagnose-patroni.sh`
Диагностика Patroni одной командой: статус StatefulSet, поды и метки, etcd, **совпадение `SCOPE/NAMESPACE` на всех подах**
(иначе split-brain), секреты, роли. Только чтение.

## 3.5. `Makefile` — «одна команда»

Переменные в начале файла можно переопределять в командной строке: `make configure MONITORING=true`, `make infra FORCE=1`.
`SHELL := /bin/bash` и `-euo pipefail` — рецепты останавливаются при первой ошибке.

| Цель | Что делает |
|---|---|
| **`make up`** | `preflight` → `infra` → `configure` → `deploy`, затем печатает адрес сайта |
| `preflight` | проверяет наличие terraform, ansible, jq, ssh, git и SSH-ключа (`id_ed25519` или `id_rsa`, определяется автоматически) |
| `tf-init` | `terraform/bootstrap-state.sh` создаёт (если нет) S3-бакет состояния; `terraform init -migrate-state` подключает его |
| `infra` | `terraform/safe-apply.sh`: сохраняет план, показывает итог и **спрашивает подтверждение, если план удаляет или пересоздаёт ресурсы** (например, ВМ вместе с данными); применяется именно сохранённый план. `FORCE=1` — без вопросов |
| `configure` | `generate_inventory.sh` → `vault.yml` с `k3s_token` (один раз) → коллекции Ansible → `ansible-playbook`, вывод **дописывается** в `ansible/last-run.log` (там пароли) |
| `deploy` | копирует `k8s/` и скрипты на ВМ и запускает `deploy-steps.sh` для последнего коммита `origin/main` |
| `github-secrets` | записывает в GitHub секреты `SSH_HOST` и `SSH_KNOWN_HOSTS` (отпечаток ВМ). Нужен `gh auth login` |
| `start` / `stop` / `status` | вручную запустить, остановить ВМ и узнать её состояние (по умолчанию ВМ включает и выключает расписание) |
| `destroy` | после подтверждения `yes` выполняет `terraform destroy` |
| `check` | те же проверки, что в CI: pre-commit, pytest с порогом покрытия, pip-audit, terraform fmt/validate, ansible-lint |

### `terraform/safe-apply.sh`
Защита от случайного удаления. Строит план во временный файл, печатает его итог, достаёт из JSON-представления плана список ресурсов,
у которых среди действий есть `delete` (в том числе пересоздание), и при их наличии требует ввести `yes`. Затем применяет **сохранённый** план,
поэтому между проверкой и применением ничего не изменится.
