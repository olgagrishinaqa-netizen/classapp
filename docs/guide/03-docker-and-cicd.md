# 3. Docker, линтеры, CI/CD, Makefile и скрипты деплоя

## 3.1. Docker-образ

**Зачем Docker.** Образ — «коробка» с приложением и всеми зависимостями: одинаково работает на ноутбуке, в CI и на сервере.

### `Dockerfile` — построчно
| Строки | Что делает и зачем |
|---|---|
| 1 | `FROM python:3.11-slim` — база: Python 3.11 в урезанном Debian (меньше размер и поверхность атаки) |
| 3–4 | `ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1` — не создавать `.pyc`; выводить логи сразу, без буфера (иначе `kubectl logs` отстаёт) |
| 6 | создаёт непривилегированного пользователя `appuser`: приложение не работает от root, при взломе ущерб меньше |
| 7 | `WORKDIR /app` — рабочий каталог |
| 9–10 | отдаёт `/app` пользователю `appuser` |
| 11–12 | создаёт каталоги для логов (`/var/log/classapp`) и метрик нескольких воркеров (`/tmp/prometheus_multiproc`), отдаёт их `appuser` |
| 14–15 | **сначала** копирует только `requirements.txt` и ставит зависимости. Этот слой кэшируется: пока зависимости не менялись, пересборка быстрая (`--no-cache-dir` — не хранить кэш pip в образе) |
| 17–18 | копирует весь код с правами `appuser` |
| 20–22 | копирует `entrypoint.sh` и делает его исполняемым |
| 24 | `USER appuser` — всё дальше (и запуск) идёт не от root |
| 26–27 | `FLASK_CONFIG=config.ProdConfig` — образ по умолчанию боевой; `PROMETHEUS_MULTIPROC_DIR` — каталог метрик |
| 28 | `EXPOSE 8000` — документирует порт приложения |
| 29 | `ENTRYPOINT ["/entrypoint.sh"]` — всегда сначала запускается скрипт проверки/ожидания БД |
| 30 | `CMD [gunicorn -w 4 -b 0.0.0.0:8000 "app:create_app()"]` — команда по умолчанию (в Kubernetes переопределяется: 1 воркер) |

### `entrypoint.sh` — построчно
| Строки | Что делает |
|---|---|
| 2 | `set -euo pipefail` — остановка при любой ошибке, при использовании пустой переменной и в конвейерах |
| 5–6 | `: "${SECRET_KEY:?...}"` — если переменная не задана, скрипт падает с понятным сообщением (fail fast) |
| 9–24 | если `DATABASE_URL` не задан, собирает его из `POSTGRES_HOST/DB/USER` и `DB_PASSWORD`; пароль кодируется `urllib.parse.quote`, чтобы спецсимволы не ломали URL |
| 26–57 | встроенный Python-скрипт ждёт готовности БД: до `DB_WAIT_ATTEMPTS` (30) попыток через `DB_WAIT_INTERVAL` (2 с) пытается подключиться через `psycopg2`; нет — выход с кодом 3. Приложение и БД стартуют одновременно, без ожидания первый запрос упал бы |
| 59–60 | `exec "$@"` — запускает основную команду (gunicorn) **заменяя** процесс скрипта: gunicorn получает сигналы остановки (graceful shutdown) |

### `gunicorn.conf.py` — метрики при нескольких воркерах
Каждый воркер gunicorn — отдельный процесс; без доработки счётчики Prometheus «прыгали» бы. `on_starting` очищает
каталог метрик при старте, `child_exit` убирает данные завершившегося воркера. Обе функции ничего не делают, если
`PROMETHEUS_MULTIPROC_DIR` не задан.

### `requirements.txt`, `requirements-dev.txt`
Первый — зависимости приложения с **точными версиями** (воспроизводимая сборка): Flask, SQLAlchemy, Alembic, WTForms,
gunicorn, psycopg2, prometheus-клиент и др. Второй — инструменты разработки: pytest, pytest-cov, pre-commit, locust, ansible-lint.

### Compose-файлы (локальные стеки)
| Файл | Назначение |
|---|---|
| `docker-compose.dev.yml` | локальная разработка: PostgreSQL 15 (порт 5433) + контейнер Python, который ставит зависимости и запускает `flask run --debug` на 8080. Код монтируется с диска |
| `docker-compose.logging.yml` | локальный стек логов: Loki (хранилище), Promtail (читает файлы логов), Grafana с готовыми дашбордами из `provisioning/` |
| `docker-compose.prod.yml` | **устаревший** docker-стек (db + web + nginx + prometheus). В деплое не используется: прод работает на K3s |
| `nginx.conf` | конфиг nginx для этого устаревшего стека (upstream `web:8000`); в Kubernetes конфиг лежит в ConfigMap в `k8s/classapp-nginx.yaml` |
| `.env.sample` | образец переменных окружения |

## 3.2. Качество кода: линтеры

**Зачем.** Единый стиль и поиск типичных ошибок до попадания кода в репозиторий. Запускаются через **pre-commit** и в CI.

### `.pre-commit-config.yaml` — построчно
| Строки | Что делает |
|---|---|
| 1–6 | исключает из проверки `.venv`, `migrations`, `alembic` |
| 9–15 | базовые проверки: пробелы в конце строк, перевод строки в конце файла, слишком большие файлы, маркеры конфликта слияния |
| 17–20 | **black** — автоформатирование кода |
| 22–25 | **isort** — сортировка импортов |
| 27–30 | **flake8** — поиск ошибок и нарушений стиля |
| 32–37 | **bandit** — поиск уязвимостей в `app/` (например, хардкод паролей, небезопасные вызовы) |

### `.flake8`, `pyproject.toml`
`.flake8`: максимальная длина строки 120, игнорировать `E203` (конфликт с black), не проверять `.git`, `__pycache__`, `.venv`, `alembic`.
`pyproject.toml`: настройки black и isort (длина строки 100, профиль `black`). Секция `[tool.flake8]` там
flake8 игнорирует (он читает `.flake8`), она оставлена как заметка.

### Прочее
`.gitignore` — что не попадает в git: окружение `.venv`, секреты `.env`, состояние и планы Terraform, `terraform.tfvars`,
сгенерированный inventory, `vault.yml`, **`ansible/last-run.log` (там пароли)**, загрузки, локальные БД.
`.gitattributes` — принудительные окончания строк LF (важно для shell-скриптов, чтобы они запускались на Linux).

## 3.3. CI/CD — GitHub Actions (`.github/workflows/`)

Три workflow выстроены в цепочку. Каждый следующий запускается по завершении предыдущего (`workflow_run`).

```
push в любую ветку --> CI --(успех)--> Build and Push to GHCR --(успех, только main)--> Deploy
```

### `ci.yml` — построчно
| Строки | Что делает |
|---|---|
| 1 | название |
| 3–8 | запуск: `push` в **любую** ветку и `pull_request` в `main` |
| 10–11 | права токена: только чтение репозитория (минимум прав) |
| 13–15 | `concurrency`: для одной ветки одновременно идёт один прогон, новый коммит отменяет старый прогон |
| 18–47 | **job `lint`**: checkout кода, Python 3.11 с кэшем pip, кэш хуков pre-commit (ключ — хэш конфига), установка pre-commit, запуск `pre-commit run --all-files --hook-stage push --show-diff-on-failure`. Любое нарушение **останавливает** пайплайн |
| 49–52 | **job `test`**, запускается после `lint` (`needs: lint`) |
| 53–56 | окружение тестов: `DevConfig`, SQLite-БД, `PYTHONPATH` |
| 67–70 | установка зависимостей и инструментов pytest |
| 72–75 | запуск тестов с покрытием; пишет `reports/junit.xml` и `reports/coverage.xml` |
| 77–83 | **выгрузка артефактов**: отчёты сохраняются в хранилище GitHub на 14 дней (`if: always()` — и при падении тестов) |
| 85–103 | **job `build-check`**: пробная сборка Docker-образа **без** отправки (`push: false`) с кэшем слоёв GitHub |
| 105–133 | **job `notify`**: после всех трёх (`needs`) и всегда (`if: always()`); если секретов Telegram нет — предупреждение и выход; иначе по результатам (`failure|cancelled` = FAILED) шлёт сообщение через Telegram Bot API (ветка, коммит, автор, ссылка на запуск) |

### `build.yml` — построчно
| Строки | Что делает |
|---|---|
| 3–7 | запуск после завершения workflow «CI» (на любой ветке) либо вручную (`workflow_dispatch`) |
| 9–12 | группа `concurrency` по ветке коммита: сборки разных веток не отменяют друг друга |
| 14–17 | права: чтение кода и **запись пакетов** (нужно, чтобы пушить образ в GHCR) |
| 25–28 | условие: ручной запуск либо успешный CI |
| 31–35 | checkout **именно проверенного коммита** (`head_sha`), а не default-ветки |
| 37–52 | определяет коммит и ветку (из события), делает «безопасное» имя ветки (`/` -> `-`, нижний регистр) и передаёт их следующим шагам через `$GITHUB_OUTPUT` |
| 54–59 | имя владельца репозитория в нижнем регистре (Docker не принимает заглавные) |
| 61–69 | Buildx и вход в ghcr.io токеном `GITHUB_TOKEN` |
| 71–79 | **сборка и отправка образа** с тегом `<ветка>-<sha>`; кэш слоёв |
| 81–87 | только для `main` дополнительно тег `latest` (без пересборки, через `imagetools create`) |
| 89–106 | уведомление в Telegram о результате сборки |

### `deploy.yml` — построчно
| Строки | Что делает |
|---|---|
| 3–6 | комментарий: единственный путь автодеплоя; `SSH_HOST` — IP ВМ |
| 8–11 | запуск после успешной сборки |
| 14–17 | job `deploy`: **только для ветки `main`** и успешной сборки; таймаут 45 минут |
| 18–21 | переменные: адрес и порт SSH из секретов, `COMMIT_SHA` — коммит, который выкатываем |
| 23–26 | checkout этого коммита |
| 28–57 | подготовка SSH: записывает приватный ключ из секрета `SSH_KEY` (права 600) и формирует `~/.ssh/config` с хостом `prod` (таймауты, keep-alive, переиспользование соединения `ControlMaster`) |
| 59–72 | ждёт доступности SSH: до 8 попыток через 15 с (на случай, если ВМ только что запущена) |
| 74–89 | загружает на ВМ папки `k8s` и `scripts/pull-deploy` одним `tar` по SSH в `/opt/classapp/repo`, до 5 повторов |
| 91–104 | запускает на ВМ `deploy-steps.sh <sha>` с переменными `IMAGE_REPO` и `SRC_DIR`, до 3 повторов |
| 106–120 | уведомление о результате деплоя |

**Секреты репозитория:** `SSH_HOST`, `SSH_KEY` (обязательные); `SSH_PORT`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (необязательные).
`GITHUB_TOKEN` выдаётся GitHub автоматически.

**Что делать, если коммит пришёл ночью** (ВМ выключена по расписанию): деплой упадёт на ожидании SSH; утром нажмите *Re-run* у workflow «Deploy to Production VM1».

## 3.4. Скрипты деплоя (`scripts/`)

### `scripts/pull-deploy/deploy-steps.sh` — шаги выкатки (общая логика)
Запускается на ВМ от root: `deploy-steps.sh <sha>`. Каждый шаг идемпотентен.

| Строки | Шаг | Что делает |
|---|---|---|
| 1–14 | заголовок | `set -euo pipefail`; параметры: коммит, репозиторий образа, каталог исходников, `KUBECONFIG`, имя образа `ghcr.io/<owner>/classapp:main-<sha>`; создаёт каталоги логов |
| 16–18 | ШАГ 1 | снимает taint (ограничение «не планировать поды») с мастер-ноды: на одной ноде все поды должны работать на ней |
| 20–34 | ШАГ 2 | применяет etcd, services и Patroni. Если StatefulSet нельзя изменить «на месте» (Kubernetes запрещает менять часть полей), пересоздаёт его с `--cascade=orphan`, не удаляя поды и данные |
| 36–50 | ШАГ 3 | ждёт до 15 минут, пока у сервиса `classapp-db-master` появится адрес (то есть Patroni выбрал лидера); при таймауте печатает диагностику |
| 52–69 | ШАГ 4 | читает из секрета `db-password`, `secret-key`, `admin-phone`, `admin-password`; собирает `database-url` (пароль URL-кодируется, `sslmode=require`); пересоздаёт секрет `classapp-secrets` через `--dry-run | apply` |
| 71–79 | ШАГ 5 | удаляет старый Job миграций, создаёт новый с образом нужного коммита (подмена тега через `sed`) и ждёт завершения до 10 минут; при ошибке показывает логи и **останавливает деплой** |
| 81–84 | ШАГ 6 | подставляет тег в `kustomization.yaml`, применяет `kubectl apply -k k8s/` (web, nginx, HPA), затем `set image` |
| 86–97 | ШАГ 7 | ждёт готовности Deployment до 5 минут; при неудаче делает **откат** (`rollout undo`) и завершает с ошибкой; затем до 15 раз проверяет `/healthz` через nginx на порту 30080 |
| 99–121 | ШАГ 8 | необязательно: ставит в Grafana аннотацию «Деплой <sha>» (вертикальная метка на графиках); если мониторинга нет — тихо пропускается |
| 123–132 | ШАГ 9 | очистка: журнал systemd старше 7 дней, неиспользуемые образы (`crictl rmi --prune`) |

### `scripts/pull-deploy/pull-deploy.sh` и `install.sh` — **запасной** pull-вариант
Вместо push по SSH можно, чтобы сама ВМ раз в 2 минуты опрашивала GitHub. `pull-deploy.sh`: берёт блокировку (`flock`,
чтобы не запускаться дважды), узнаёт последний коммит `main` (`git ls-remote`), проверяет, что образ `main-<sha>` уже есть в GHCR
(то есть CI и сборка прошли), затем запускает `deploy-steps.sh`. Неудачный коммит повторяется до 3 раз. Результат — в Telegram.
`install.sh` ставит скрипт и systemd-юниты (service + timer). По умолчанию таймер **не включается** (чтобы не конкурировать с `deploy.yml`);
включить: `sudo bash install.sh --enable`.

### `scripts/diagnose-patroni.sh`
Диагностика Patroni одной командой: статус StatefulSet, поды и метки, etcd, **совпадение `SCOPE/NAMESPACE` на всех подах**
(иначе split-brain), секреты, роли. Только чтение.

## 3.5. `Makefile` — «одна команда» — построчно

| Строки | Что делает |
|---|---|
| 1–11 | описание целей |
| 13–14 | запуск рецептов в bash с `-euo pipefail` (останавливаться при ошибке) |
| 16–24 | переменные: каталог Terraform, пользователь SSH, **автоопределение SSH-ключа** (`id_ed25519` или `id_rsa`), ветка деплоя, регион, переключатель мониторинга. Любую можно переопределить: `make configure MONITORING=true` |
| 26 | `.PHONY` — эти цели не файлы |
| 28–31 | **`make up`** = `preflight` -> `infra` -> `configure` -> `deploy`, затем печатает адрес |
| 33–38 | `preflight`: проверяет наличие terraform, ansible, jq, ssh, git и SSH-ключа |
| 40–44 | `tf-init`: скрипт `bootstrap-state.sh` создаёт (если нужно) S3-бакет состояния и печатает параметры backend; `terraform init -migrate-state` подключает его и при первом запуске переносит локальное состояние |
| 46–48 | `infra`: `terraform apply` с публичным ключом из `~/.ssh` |
| 50–61 | `configure`: генерирует inventory из вывода Terraform; создаёт `vault.yml` с `k3s_token` один раз; ставит коллекции Ansible; запускает playbook, **дописывая** вывод в `ansible/last-run.log` (там пароли); ограничивает права лога |
| 63–72 | `deploy`: узнаёт IP и последний коммит `origin/main`, по SSH копирует `k8s` и скрипты и запускает `deploy-steps.sh` |
| 74–81 | `start` / `stop` / `status`: вручную запустить/остановить ВМ и узнать её состояние |
| 83–86 | `destroy`: переспрашивает `yes`, затем `terraform destroy` |
| 88–94 | `check`: те же проверки, что в CI, плюс `terraform validate`, `fmt -check`, `ansible-lint` |
