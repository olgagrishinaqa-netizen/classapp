## 0. Общая картина (выучить наизусть)

Тесты лежат в `tests/` и запускаются командой `pytest`. Их пять слоёв, от мелкого к крупному:

| Слой | Файлы | Что проверяет | Браузер |
|---|---|---|---|
| 1. Юнит | `test_models.py`, `test_helpers.py`, `test_config.py`, `test_app_factory.py` | Отдельные функции и настройки: хэш пароля, нормализация телефона, fail-fast конфига прода | нет |
| 2. Интеграция (бэкенд) | `test_pages_*.py`, `test_api.py`, ранее существовавшие `test_auth.py`, `test_tasks.py` и др. | Страницы и формы целиком: запрос → БД → ответ, для ролей аноним / родитель / админ | нет |
| 3. HTML-шаблоны | `test_frontend_html.py` | Структура страниц, ссылки, кнопки по ролям, доступность (метки у полей) | нет |
| 4. Безопасность | `test_frontend_security.py` | XSS-экранирование, CSRF, флаги session-cookie | нет |
| 5. E2E | `tests/e2e/` | Настоящий Chromium: JavaScript, диалоги, вкладки, карусель, подтверждение удаления | да (Playwright) |

**Одна фраза:** пирамида тестов. Внизу много быстрых тестов без браузера, наверху мало медленных, зато проверяющих то, что видит пользователь.

Запуск:

```bash
pytest                      # слои 1–4, без браузера, быстро
pytest -m e2e               # слой 5, нужен Playwright и Chromium
pytest --cov=app --cov=config --cov-fail-under=95   # как в CI
make check                  # линтеры + тесты с порогом покрытия 95%
```

`pytest.ini` содержит `addopts = -m "not e2e"`, поэтому обычный `pytest` E2E не трогает. В CI для E2E есть отдельная задача `e2e`.

## 1. Общая основа: `tests/conftest.py`

Фикстура pytest — это заготовка, которую тест получает, написав её имя в аргументах.

| Фикстура | Что даёт |
|---|---|
| `app` | Приложение Flask на всю сессию, одна БД |
| `client` | Анонимный клиент |
| `admin_client`, `parent_client` | Клиенты, уже вошедшие под нужной ролью |
| `make_user` | Фабрика пользователей, которая удаляет их после теста |
| `wipe(Model, ...)` | Очищает таблицы до теста и повторно после него |
| `upload_dir` | Временная папка для загрузок, подменяет `UPLOAD_FOLDER` |
| `_clean_session` | Автоматически откатывает и очищает сессию БД |

**Зачем столько очистки.** БД одна на весь прогон, поэтому тест не должен оставлять за собой строки. Пока этого не было, старые тесты падали из-за дубликатов телефона и учеников, оставшихся от новых.

Пример теста слоя 2 из `tests/test_pages_news.py`:

```python
def test_parent_cannot_publish(self, parent_client, clean_news):
    response = parent_client.post(
        "/news",
        data={"title": "Взлом", "description": "Д", "status": "published"},
        follow_redirects=True,
    )
    assert "Публиковать новости может только администратор." in text(response)
    assert News.query.count() == 0
```

Тест проверяет два факта: пользователь увидел отказ, и в БД ничего не появилось. Проверять только текст на странице недостаточно.

## 2. Что покрывает каждый слой

### Слой 1. Юнит
- `test_config.py`: прод падает при старте без `SECRET_KEY` и `DATABASE_URL` (fail-fast), `SESSION_COOKIE_SECURE` включается переменной окружения, значения по умолчанию. Для проверки разбора переменных окружения модуль `config` перезагружается фикстурой `reload_config`, потому что значения вычисляются при импорте.
- `test_models.py`, `test_helpers.py`: хэш пароля, нормализация телефона, сохранение файлов, маскирование телефона в логах.

### Слой 2. Интеграция
На каждую страницу один и тот же набор: нужен вход, права по ролям, успешный случай, пустые и неверные поля, несуществующий id, дубликат. Примеры:
- Финансы (`test_pages_finance.py`): баланс равен взносам минус расходы, сумма с запятой `100,50` принимается, `0`, `-5` и `abc` отклоняются, чек другого типа (`.exe`) отклоняется, а при правке без файла старый чек сохраняется.
- Новости: родитель не видит черновики, не больше 10 изображений, при удалении новости удаляются и файлы.

Параметризация (`@pytest.mark.parametrize`) прогоняет один тест на многих входных данных, поэтому набор плохих сумм записан одной строкой.

### Слой 3. HTML
BeautifulSoup разбирает отрисованную страницу. Проверки: один `<h1>`, нет битых внутренних ссылок (проверяющий обходит навигацию), у админа есть кнопки управления, у родителя их нет, у полей есть `label`.

### Слой 4. Безопасность
- **XSS.** В каждое пользовательское поле записывается `<script>`, затем на странице проверяется, что он выведен экранированным. Для колонки `room` (`VARCHAR(40)`) используется короткая строка `SHORT_PAYLOAD`, иначе PostgreSQL отклонял длинную.
- **CSRF.** Приложение с включённой защитой должно отклонять форму без токена.
- **Cookie.** Проверяются флаги `HttpOnly` и `SameSite=Lax` на боевом классе `BaseConfig`.

### Слой 5. E2E (`tests/e2e/`)
Единственный слой, где выполняется JavaScript. Фикстуры из `tests/e2e/conftest.py`:
- `live_server` — настоящий Flask в потоке на свободном порту, чистая БД на каждый тест.
- `page` — страница Chromium; блокирует внешние запросы, подменяет Tailwind CDN заглушкой (поэтому тесты не зависят от интернета), после теста падает, если в консоли были ошибки JavaScript. При падении сохраняет скриншот в `reports/e2e-failures/`.
- `login`, `admin_page`, `seed` — вход и подготовка данных.

Сценарии: маска телефона и показ пароля, регистрация, выход, смена роли, тема, диалоги подтверждения удаления, вкладки, карусель, «здоровье» всех страниц.

## 3. Приёмы, о которых могут спросить

**`xfail(strict=True)`** — «ожидаемое падение». Баг известен и записан в причине. Если баг исправят, тест неожиданно пройдёт и станет красным (strict), напоминая убрать метку. Так в наборе записаны 5 известных проблем доступности (поля без `label` на /login, /schedule, /bell-schedule, /users, /admin/students).

**Покрытие 95%.** Измеряется `pytest-cov` по `app` и `config`; CI падает ниже порога (`--cov-fail-under=95`). Три защитных строки в `routes.py` недостижимы через HTTP, поэтому остаётся запас.

**SQLite и PostgreSQL.** Локально тесты идут на SQLite, в CI матрица из двух БД. Они различаются: SQLite не проверяет длину строк и по умолчанию не включает внешние ключи. На этом CI поймал `VARCHAR(40)`.

**Изоляция тестов.** Каждый тест чистит за собой, порядок запуска не влияет на результат.

## 4. Честные ограничения (лучше сказать самой)

- **CSRF на формах удаления, завершения и выхода** не проверяется тестами; по чтению кода защита там не подтверждена.
- **Некорректное число при правке расписания** (например, нечисловое значение) вызывает 500 вместо сообщения об ошибке; найдено чтением кода, в тестах не закрепляется.
- **E2E только в Chromium**, без Firefox и Safari, размер экрана мобильный.
- **Нагрузочные тесты** лежат отдельно в `tests/load/` и в обычный набор не входят.
- **Покрытие строк не равно покрытию логики:** 95% говорит, что строки исполнялись, но не что проверены все сочетания данных.

## 5. Вопросы и ответы для защиты

**Чем ваши тесты отличаются от «я кликала руками»?**
Они запускаются одной командой и на каждый push в CI, воспроизводимо и без меня. Сломанная регистрация или права доступа видны сразу, а не у пользователя.

**Почему E2E на Python, а не на JavaScript (Cypress)?**
Тесты живут в одном репозитории с бэкендом, переиспользуют модели и подготовку данных, и в CI один язык и один набор зависимостей.

**Как вы обеспечили, что тесты не зависят друг от друга?**
Фикстуры `wipe`, `_clean_session` и `make_user` чистят БД до и после, телефоны генерируются уникальными, `upload_dir` временная.

**Зачем E2E, если есть интеграционные тесты?**
Интеграционные не исполняют JavaScript. Диалог подтверждения удаления, маска телефона, карусель и вкладки проверяются только в браузере.

**Зачем нужен `xfail` вместо того, чтобы просто починить?**
Он фиксирует известный долг как проверяемый факт. Когда баг починят, тест сам подскажет убрать метку.

**Что делает CI с тестами?**
Задача `test` идёт в матрице SQLite и PostgreSQL с порогом 95%, задача `e2e` запускает Chromium; `deploy` на main идёт только после зелёного CI.

**Что бы вы добавили дальше?**
Исправить 5 пробелов доступности и убрать `xfail`, проверить CSRF на POST-формах удаления и выхода, обработать некорректные числа в формах расписания, добавить Firefox в E2E.
